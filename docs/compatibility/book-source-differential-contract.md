# Book Source Differential Compatibility Contract

Evidence baseline: `14dd24945b2914ce2708b8abaa4ee67ceef892af`
Decision approved: 2026-08-19 UTC

## Verdict

- **CONFIRMED** - The frozen runtime exposes a stateful search -> book information -> table of contents -> chapter content pipeline. Requests, redirects, runtime configuration, source-visible cache surfaces, persistent chapter records, rule variables, retained bodies, cookies, parsed models, partial results, and errors can affect later stages.
- **CONFIRMED** - The repository does not contain a complete offline four-stage fixture corpus. Its bundled Book Source uses external services, login state, JavaScript, and live responses, so it cannot be the repeatable compatibility oracle.
- **DECISION** - Compatibility is proved against immutable goldens generated by running the frozen Legado baseline against a controlled local replay server. A live site is never the oracle.
- **DECISION** - A Book Source is compatible on one platform only when every stage and capability it reaches passes this contract on that platform. An all-platform claim requires Android, iOS, Windows, macOS, and Linux to pass.
- **DECISION** - The contract preserves source-observable behavior, including behavior that appears unusual. It does not require Liber to reproduce Kotlin exception classes, stack traces, logs, or internal implementation defects.
- **DECISION** - Liber may fix a baseline resource leak when the fix has no source-observable effect. If matching observable behavior would violate an approved security or data-integrity prohibition, the result is `policy-rejected`, not pass.

## Boundary

The differential boundary starts with an already accepted, semantically parsed Book Source object. JSON import validation, unknown-field round trips, migration, and security approval are separate contracts.

The oracle executes the same scenario inputs against Legado and Liber:

1. Search with an explicit keyword and page.
2. Book information with the selected search result and current book state.
3. Table of contents with current book state and any retained response or variables.
4. Chapter content with the selected chapter, next-chapter context, and current state.

A scenario may stop before stage 4 when that is the source's reachable behavior. Passing one early stage never implies that a later reachable stage is compatible.

## Matching Rules

### Requests

The comparator MUST match the causal request trace. Sequential requests and every redirect hop are ordered. Requests in one declared concurrent batch are compared as a multiset with the same dependencies; wall-clock start and completion order are not compared.

The following values are strict:

- HTTP method;
- resolved request path and query, including ordering and encoding;
- values and duplicate ordering of source-controlled headers;
- request body bytes;
- ordered outbound attempt trace and redirect method/body behavior;
- final effective URL;
- actual outbound cookies.

Header-name case and ordinary header ordering are ignored. Platform-generated `Host`, `Content-Length`, `Accept-Encoding`, and `Connection` are ignored unless the source explicitly sets them. No general URL, body, or text cleanup is allowed.

Every attempt is classified as `initial`, `redirect`, `source-status-retry`, or `transport-retry`. HTTP non-2xx responses are not automatically network errors: the frozen client retries as configured and returns the last response body to the parser. Connection failures propagate as failures. Fixtures MUST cover both paths.

### Outputs

Ordered arrays, strings, booleans, URLs, numbers, and the observable distinction between `null`, empty, partial, and absent values MUST match the frozen golden after the frozen runtime's own normalization. JSON object key ordering is ignored. No global fuzzy comparison, whitespace cleanup, or wildcard mask is allowed.

A field-specific comparator is allowed only for an inherently dynamic capability fixture. It MUST name that field and assert its semantic relationship. Ordinary fixtures MUST not depend on current time or randomness.

Two frozen behaviors require named field-specific assertions rather than broad masks:

- operation timestamps are checked against the recorded operation interval and required ordering relationships, not for cross-run equality;
- oversized-cookie eviction is checked for the frozen size bound and survivor-map relationship, not for the identity of randomly evicted keys.

### Concurrency and timing

Concurrent pagination MUST produce the same final ordered chapters or content even when request completion order varies. Tests assert the configured maximum concurrency, rate-limit semantics, and causal batches rather than exact millisecond timings.

Timeout and cancellation fixtures compare:

- whether the operation ends within the fixture's bounded window;
- whether requests and scripts stop;
- whether partial output or state survives;
- whether WebView, response-body, and temporary resources are cleaned up.

Cleanup has two distinct assertions:

- source-observable cleanup effects, including cookies, storage, requests, and state visible to a later scenario step, MUST match the frozen result;
- Liber's own WebView, response-body, and temporary resources MUST be released, even when the frozen implementation leaks them without a source-observable effect.

A non-observable baseline resource leak is therefore not part of the golden equality check. Fixing it remains a pass. If the source-observable baseline effect cannot be reproduced without violating an approved security or data-integrity prohibition, the fixture is `policy-rejected`.

### Cookies and state

Cookie comparison follows the frozen baseline's effective behavior, not an idealized browser model. The fixture records:

- effective name/value maps per baseline domain key;
- session versus persistent storage;
- outbound Cookie values for every request;
- response, redirect, HTTP-to-WebView, and WebView-to-HTTP synchronization;
- overwrite, removal, restart, and cleanup results.

RFC cookie attributes that the frozen baseline discards do not need to be retained for their own sake, but Liber MUST produce the same effective requests and restart behavior.

Fixtures are isolated by default. Before a fixture starts, the harness MUST reset and seed only declared state, then prove that no undeclared reachable state can affect the path. Declared state includes:

- every consumed baseline runtime setting, including the default user agent, HTTP transport selection, pagination thread count, and TOC word-count setting when reachable;
- every reachable source-visible cache key and semantic storage category exposed to rules, including persistent, memory, binary/file, and typed in-process caches, plus login header and login information;
- relevant persistent records read or written by the stage, including chapter rows;
- process-global request state that can affect source-visible behavior, including source-keyed rate-limiter records;
- shared JavaScript scope, HTTP and platform WebView cookies, source-visible WebView local/session storage, source/book/chapter variables, and retained bodies.

After each step, the harness compares every declared state surface, the semantic value of every reachable source-visible cache key/storage category, the source-visible effect of process-global request/rate-limiter state, and the fields of every persistent record that the step read or wrote. Internal cache encoding and database layout are not compatibility surfaces. An adapter that cannot reset, seed, or observe required state, or cannot prove undeclared reachable state irrelevant, produces a coverage gap, not pass.

A stateful scenario explicitly chains stages in one session without resetting between steps. It records the declared initial state and compares every listed state surface after each step.

## Error Equivalence

Errors are compared by stage and stable category:

- invalid runtime configuration;
- network failure;
- timeout;
- cancellation;
- empty response;
- rule or parser failure;
- empty required result;
- JavaScript or resource-limit failure;
- WebView failure.

Exception class, localized message, stack trace, and debug log are not compatibility surfaces. Partial result versus total failure, and state mutation versus no mutation, are compatibility surfaces.

Liber MUST preserve behavior that a source can observe through requests, state, or final output. For example, if the frozen baseline parses a useful non-2xx response body, Liber cannot reject that response merely because rejecting it appears more conventional. Liber does not need to reproduce an incidental Kotlin exception when the same stable failure, state, and partial-output result can be produced directly.

A behavior prohibited by an approved security or data-integrity policy is not silently normalized into a pass. Its fixture receives `policy-rejected`, and every source that requires it remains incompatible.

## Corpus Construction

### Authority

The authoritative corpus is versioned, offline, and served by a local replay server. Any unmatched outbound request fails the fixture; external network fallback is forbidden.

Each fixture or multi-stage scenario contains, logically:

- a stable fixture ID and corpus version;
- capability-matrix references;
- target platform and, for WebView fixtures, native adapter identity;
- the exact Book Source semantic input;
- complete initial runtime configuration, all reachable source-visible cache-key/storage-category values, relevant persistent-record fields, process-global request/rate-limiter state, browser state, and network state;
- replay responses and expected inbound requests;
- scenario operations;
- frozen request trace, outputs, state transitions, terminal verdict, and cleanup observations;
- baseline SHA and hashes of all fixture inputs and golden artifacts.

This ticket does not prescribe a final on-disk JSON Schema. The prototype tickets may choose the smallest representation that preserves these fields.

### Selection rule

Fixtures are selected from a capability matrix derived from reachable frozen source branches and documented rule forms, not from site popularity. The matrix MUST cover at least:

- HTML, malformed/tolerant HTML, JSON, text, XML handling, CSS, XPath, JSONPath, Regex, and JavaScript rule paths;
- GET, query encoding, POST form, POST JSON, explicit content type, headers, cookies, redirects, retries, non-2xx bodies, and WebView-backed requests;
- search list, detail-page fallback, book information, single/multi-page TOC, volume nodes, single/multi-page content, content replacement, entities, relative URLs, and retained bodies;
- source, book, and chapter variables; shared JavaScript scope; login check; all reachable cache keys/storage categories including login header/information cache; HTTP/WebView cookie transfer; restart behavior; process-global rate-limiter state; runtime user agent and HTTP transport selection; pagination thread count; TOC word-count mode and required chapter records; operation timestamps; oversized-cookie eviction;
- empty and missing values, partial field failures, empty list/content, parser failure, timeout, cancellation, resource limits, and cleanup;
- sequential and concurrent pagination plus rate limiting;
- every cross-stage dependency, not merely each isolated feature.

A fixture may be synthetic, but its rule form MUST be traceable to the frozen implementation or its bundled first-party help/examples. Preserved real-source responses may supplement the corpus, but live success is not a gate and cannot replace a missing capability fixture.

Every WebView capability fixture expands into five independent executions identified by platform and native adapter: Android WebView, iOS WKWebView, macOS WKWebView, Windows WebView2, and Linux WebKitGTK. A result cannot be copied or inferred from another adapter. A missing, `not-run`, failed, or `policy-rejected` adapter execution blocks the all-platform source claim.

A capability with no fixture is a declared coverage gap. A gap blocks every aggregate claim that depends on that capability.

### Golden generation

Goldens MUST be produced by actually running the frozen Legado SHA against the replay server. Hand-authored expectations may help review a fixture but cannot establish compatibility.

A golden records the baseline SHA, fixture hashes, request trace, stage outputs, state transitions, error result, and cleanup result. Liber CI may compare against committed goldens. Adding or changing a fixture requires rerunning the frozen oracle and updating provenance; editing only the expected output is invalid.

### Reader replace-rule stage (#17)

The prepared corpus at `tool/replace_rule_oracle/fixtures.json` covers the
frozen reader's replace-rule entry points: no rules, content-only, title-only,
both paths, regex and literal rules, name/origin scope and exclusion, ordering,
duplicated titles, `reSegment`, simplified/traditional conversion, timeout, and

`ContentProcessor.getContent(includeTitle=false)`, including the final paragraph

cannot substitute for frozen
execution. Timeout's frozen restart and stack-trace content side effects remain
a named `notCompared` observation rather than a normalized result.

## Verdict Aggregation

| Level | Allowed verdicts and pass rule |
|---|---|
| Fixture/platform | `pass`, `fail`, `policy-rejected`, or `not-run` |
| Capability/platform | Pass only when every required fixture passes and no coverage gap remains |
| Source/platform | Pass only when every capability reached by that source passes |
| Source/all-platforms | Pass only when the source passes on Android, iOS, Windows, macOS, and Linux |
| Frozen-baseline complete | Pass only when the capability matrix has no gap, every required fixture passes on all five platforms, and no baseline-supported source is policy-rejected |

`not-run`, a coverage gap, or `policy-rejected` blocks the next aggregate compatibility claim. Reports MAY state narrower platform or capability results, but MUST not shorten them to an unqualified "compatible" claim.

## Downstream Prototype Gate

Tickets 11, 12, and 13 may use smaller subsets, but every prototype result MUST provide:

1. the capability-matrix rows, target platform, and native adapter identity it exercises;
2. replay fixture and input hashes;
3. a golden generated by the frozen oracle;
4. Liber observations under the same inputs;
5. comparator output using this contract;
6. explicit `not-run`, gap, and policy-rejection entries.

The architecture and security tickets remain blocked until their required prototype subsets pass or return an explicit incompatibility that forces a map decision.

## Policy divergences

`policy-rejected` above decides a *fixture's* status. These are the places where this product knowingly does not
reproduce baseline behavior, recorded here so no row is normalized into a pass later and so a claim that "the
divergence is in the differential contract" has something to point at:

- **TLS trust.** The baseline trusts every certificate and every hostname for every source request
  (`HttpHelper.kt:63,65` — `unsafeSSLSocketFactory` plus `unsafeHostnameVerifier`). This product validates by
default: a certificate or hostname failure is a named outcome, the user is asked once per source and host, and
the exception the confirmation stores is what the transport reads afterwards (ADR 0011 §5, #30). A fixture that
needs the baseline's trust is `policy-rejected` until the user has granted that exception for the source under
test; no fixture grants one today.
- **Cookie trimming.** The baseline evicts random pairs from its cookie store to stay at 4 096 characters
  (`CookieStore.kt`); this product bounds the session jar differently and does not reproduce the random
  eviction (ADR 0011 §3).
- **Cache capacity and eviction order.** The baseline's persistent `caches` table is unbounded; only its
  in-memory `LruCache` is capped (50 MB, `CacheManager.kt:20-27`), and that cap is global to the process and in
  access order, so a read promotes an entry. This product persists a source's entries in the space's
  `source_entries` and caps a source's `cache.*` bucket at the frozen 600 rows, evicting the least recently
  *written* row of the bucket a write overflows (#37). A read of an entry is served from the in-memory copy and
  writes nothing, so it does not refresh the order; a source that keeps more than 600 live cache keys, or relies
  on read-recency to keep one alive, loses its oldest written keys.
- **`java.put`/`java.get` allowance.** The baseline stores those variables as ordinary cache rows in the same
  unbounded global key space (`v_<sourceKey>_<key>`, `BaseSource.kt:220-233`). This product gives them their own
  600-row bucket per source, next to the `cache.*` bucket, so cache churn cannot evict a login variable and the
  two buckets are bounded separately (#37).

A source's *cookie* rows are still not bounded per source: the baseline's trim is the only cookie cap the
frozen implementation has and it stays a recorded divergence above (#37 leaves cookie ownership and visibility
as ADR 0011 §3 fixed them).

The cookie *key* is not a divergence but an implementation gap: the baseline keys cookies by the registrable
domain (`NetworkUtils.getSubDomain`) and this product still keys them by the exact host; #21 moves it to the
registrable domain with a per-site-group visibility rule (ADR 0011 §3). The capability matrix carries the row.
